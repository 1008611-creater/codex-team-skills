# Agent Team 三窗口工作流

这套方法的目标不是增加流程，而是让复杂任务更准、更省上下文、更容易复盘。

核心原则：

- 先分级，再决定是否拆窗口。
- 一个窗口只做一个角色。
- 需求、实现、验收分离。
- 所有需求、任务、验收项都用编号交接。
- 验收必须有证据。
- 返工通过 issue 闭环。

## 任务分级

### S 级：小任务

适用：

- 改错别字。
- 改一行配置。
- 小样式调整。
- 明确报错修复。

流程：单窗口直接做。

### M 级：中等任务

适用：

- 单模块业务改动。
- 少量前后端联动。
- 有明确验收点。

流程：需求分析 + 工作实现，可轻量验收。

### L 级：复杂任务

适用：

- 涉及权限、数据库、多模块、核心业务或上线风险。
- 涉及订单、支付、用户、内容审核等核心链路。
- 需要可追踪验收证据。

流程：需求分析窗口 -> 工作实现窗口 -> 验收窗口 -> issue 返工 -> 复验归档。

### XL 级：高风险任务

适用：

- 支付、订单、用户权限、数据迁移、核心链路。
- 做错会造成业务损失。

流程：三窗口 + 更严格证据 + 必要时拆多个工作窗口。

## 默认文件结构

默认只创建这 3 个 Markdown：

```text
docs/agent-team/
  task-spec.md
  worker-report.md
  review-report.md
  issues.json        # 可选，有问题时再创建
  evidence/          # 可选，需要截图、日志、接口响应时再创建
```

## 编号规则

- 需求点：`REQ-001`
- 非目标：`NON-001`
- 业务规则：`RULE-BIZ-001`
- 权限规则：`RULE-AUTH-001`
- 数据规则：`RULE-DATA-001`
- 实现任务：`TASK-001`
- 验收项：`AC-001`
- 问题：`ISSUE-001`

后续窗口只引用编号，不重复粘贴大段需求。

## 三个窗口职责

### 需求分析窗口

只负责：

- 明确背景和目标。
- 拆范围和非目标。
- 写业务、权限、数据规则。
- 写推荐实现步骤。
- 写可执行验收标准。
- 写待确认事项。

禁止：

- 写业务代码。
- 判断最终验收通过。
- 用“正常处理”“尽量优化”“适配一下”这类模糊描述。

输出：

- `docs/agent-team/task-spec.md`

### 工作实现窗口

只负责：

- 读取 `task-spec.md`。
- 做可执行性复核。
- 按规格实现。
- 自测。
- 记录变更和风险。

禁止：

- 私自改需求。
- 降低验收标准。
- 顺手做无关重构。
- 宣布验收通过。

输出：

- `docs/agent-team/worker-report.md`

最终只能说：已实现并自测，等待验收。

### 验收窗口

只负责：

- 读取 `task-spec.md`、`worker-report.md`、代码 diff 和必要证据。
- 按 `AC` 编号逐项验收。
- 运行必要测试。
- 前端用浏览器验证。
- 接口用请求验证。
- 数据库相关检查数据结果。
- 有问题时记录复现步骤、预期、实际和证据。

禁止：

- 修代码。
- 改需求。
- 无证据给 `PASS`。

输出：

- `docs/agent-team/review-report.md`
- 有问题时创建 `docs/agent-team/issues.json`

结论只能是：`PASS` / `FAIL` / `BLOCKED`。

## Issue 闭环

`issues.json` 状态：

- `OPEN`：验收发现问题，等待修复。
- `FIXED_WAIT_RETEST`：工作窗口已修复，等待复验。
- `CLOSED`：验收窗口复验通过。
- `BLOCKED`：被外部条件阻塞。
- `WONT_FIX`：经确认本轮不处理。

硬规则：

- `CLOSED` 只能由验收窗口标记。
- 工作窗口不能关闭自己修复的问题。
- `WONT_FIX` 必须写原因。
- 每个 issue 必须绑定至少一个 `AC` 或 `REQ`。
- 返工时，工作窗口默认只读 `issues.json`、相关 `AC` / `REQ` 和相关代码。

## 准确度检查

进入实现前检查：

- 每个 `REQ` 是否有对应 `AC`。
- 每个 `AC` 是否能执行。
- 权限、数据、边界条件是否写清。
- 非目标是否足够明确。
- 待确认事项是否会阻塞实现。

进入验收前检查：

- `worker-report.md` 是否列出修改文件。
- 是否说明覆盖了哪些 `REQ` / `AC`。
- 是否记录自测命令和结果。
- 是否说明未覆盖项。

给出 `PASS` 前检查：

- 所有必选 `AC` 是否通过。
- 是否无 `OPEN` / `FIXED_WAIT_RETEST` 的阻塞 issue。
- 是否有测试、截图、接口响应或日志证据。
- 是否确认旧功能没有明显回归。

## 一句话

小任务直接做，复杂任务三窗口；少建文件，不降标准；少聊过程，多留证据。
